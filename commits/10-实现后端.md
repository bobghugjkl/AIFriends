## 一、这次提交做了什么

实现了用户认证系统的后端 API——**注册、登录、退出、刷新令牌**四个接口。替换了之前直接使用 `simplejwt` 内置视图的简单做法，改为自己封装逻辑：登录/注册时创建 JWT 并把 Refresh Token 存到 HttpOnly Cookie 里，退出时删除 Cookie。

## 二、使用了什么技术

| 技术 | 用途 |
|------|------|
| Django REST Framework (`APIView`) | 基于类的视图，自带 JSON 解析、认证集成和浏览器可测试界面 |
| JWT (`rest_framework_simplejwt`) | 生成 Access Token（短时效）和 Refresh Token（长时效），实现无状态认证 |
| HttpOnly Cookie | Refresh Token 存入 Cookie 并设 `httponly=True`，JS 无法读取，有效防御 XSS 攻击（XSS是什么？跨站脚本攻击——黑客在你的网页里注入了一段恶意JavaScript代码例如`<script>偷走token发到黑客服务器</script>`，如果token存在localStorage或普通cookie中，这段恶意代码能直接读走。但标记了HttpOnly的cookie，浏览器禁止任何JavaScript访问它，恶意脚本也就无从偷起。就像把贵重物品锁进保险柜——你自己通过正常流程（HTTP请求）能用，但小偷撬不开） |
| `django.contrib.auth.authenticate` | Django 内置认证函数，验证用户名密码并返回 `User` 对象 |
| `IsAuthenticated` 权限类 | DRF 的权限控制，要求请求携带有效 Access Token |
| Token 轮换 (`ROTATE_REFRESH_TOKENS`) | 每次刷新发放新 Refresh Token 并使旧 Token 失效，防止长期盗用 |

## 三、整体架构 / 数据流

### 登录注册认证流程

```
┌──────────┐    POST /api/user/account/login/     ┌──────────┐
│ Browser  │  ──────────────────────────────────→  │  Django  │
│          │    {username, password}               │  Server  │
│          │                                       │          │
│          │  ←──────────────────────────────────  │          │
│          │    JSON: {access, user_id, username,  │          │
│          │           photo, profile}             │          │
│          │    Set-Cookie: refresh_token=...      │          │
│          │       (HttpOnly, Secure, SameSite)    │          │
└────┬─────┘                                       └──────────┘
     │                                                     │
     │ JS 将 access 存内存用于 API 请求                      │
     │ Cookie 中的 refresh 由浏览器自动管理                  │
     │                                                     │
     ▼                                                     ▼
  后续 API 请求携带:                         Django Server:
  Authorization: Bearer <access>            1. authenticate() 验证密码
  自动携带 Cookie: refresh_token=...        2. RefreshToken.for_user() 生成 JWT
                                           3. Response + set_cookie()
```

### Token 生命周期

```
注册/登录
    │
    ▼
Access Token（2小时过期）            Refresh Token（7天过期）
    │                                       │
    ├── 用于 API 鉴权                        ├── 存 HttpOnly Cookie
    ├── 前端存内存（变量）                   ├── JS 无法读取
    └── 每次请求放 Header                    └── 过期后自动清除
         │                                       │
         ▼                                       ▼
  访问受保护 API                          Access Token 过期时
  (需 Authorization: Bearer token)        用 Refresh Token 换新
                                                 │
                                                 ▼
                                        POST /api/user/account/refresh_token/
                                        自动携带 Cookie → 服务端验证
                                        生成新 Access + 新 Refresh（轮换）
                                        旧 Refresh Token 失效
```

### 四个 API 接口

```
POST /api/user/account/register/   → 创建 User + UserProfile，返回 JWT，设 Cookie
POST /api/user/account/login/      → 验证密码，返回 JWT，设 Cookie
POST /api/user/account/logout/     → 删除 Cookie（需已登录，IsAuthenticated）
POST /api/user/account/refresh_token/ → 用 Cookie 中的 Refresh 换新 Token
```

## 四、为什么不用 simplejwt 内置的视图了

第 1 次提交时，`urls.py` 里直接用 simplejwt 的 `TokenObtainPairView` 和 `TokenRefreshView`——两个 Token 都通过 JSON 返回给前端，前端自己存。

这个方案有两个问题：
1. **安全风险**：Refresh Token 存在浏览器 localStorage 或 JS 变量中，XSS 攻击可以偷走它（localStorage 对 JS 完全可读）
2. **不灵活**：登录时需要同时返回用户信息（用户名、头像等），内置视图只返回 token

本次改为自己写视图，把 Refresh Token 存在 **HttpOnly Cookie** 里（JS 完全无法读取），只把 Access Token 通过 JSON 返回。Cookie 中的 Refresh Token 会被浏览器自动附加到每个同源请求中。

## 六、登录接口——`LoginView`

**文件**：`backend/web/views/user/account/login.py`

```python
from django.contrib.auth import authenticate
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework_simplejwt.tokens import RefreshToken

from web.models.user import UserProfile


class LoginView(APIView):
    def post(self, request, *args, **kwargs):
        try:
            username = request.data.get("username").strip()
            password = request.data.get("password").strip()
            if not username or not password:
                return Response({
                    'result': '用户名和密码不能为空'
                })
            user = authenticate(username=username, password=password)
            if user:  # 用户名密码正确
                user_profile = UserProfile.objects.get(username=username)
                refresh = RefreshToken.for_user(user)  # 生成jwt
                response = Response({
                    'result': 'success',
                    'access': str(refresh.access_token),
                    'user_id': user.id,
                    'username': user.username,
                    'photo': user_profile.photo.url,  # 必须加url！！！
                    'profile': user_profile.profile,
                })
                response.set_cookie(
                    key='refresh_token',
                    value=str(refresh),
                    httponly=True,
                    samesite='Lax',
                    secure=True,
                    max_age=86400 * 7,
                )
                return response
            return Response({
                'result': '用户名或密码错误'
            })
        except:
            return Response({
                'result': '系统异常，请稍后重试'
            })
```

**逐行讲解：**

- `class LoginView(APIView):` —— 继承 DRF 的 `APIView`。`APIView` 是 Django 普通 `View` 的增强版，自带 JSON 解析、异常处理、认证鉴权集成、浏览器可测试界面等功能。

- `def post(self, request, *args, **kwargs):` —— 只处理 POST 请求。如果用户用 GET 访问这个 URL，Django 会返回 405 Method Not Allowed。登录提交用 POST 是行业惯例——POST 表示"提交数据执行操作"。

- `request.data.get("username").strip()` —— 从请求体（JSON 或表单）中取 `username` 字段。`.data` 是 DRF 的属性，会自动根据 Content-Type 解析请求体；`.get()` 用 `[]` 如果字段不存在会返回 `None` 而不是抛出 `KeyError`；`.strip()` 去掉首尾空白字符

- `if not username or not password:` —— 空值判断。`not ""` = `True`。如果用户名或密码为空（空字符串或 None），直接返回错误

- `authenticate(username=username, password=password)` —— Django 内置的认证函数。它做两件事：
  1. 去数据库 User 表里找 username 匹配的记录
  2. 用密码学方法验证输入的密码和数据库中加密存储的密码哈希是否匹配
  3. 匹配成功返回 `User` 对象，失败返回 `None`

- `if user:` —— 如果认证成功（user 不是 None）

- `user_profile = UserProfile.objects.get(username=username)` —— 从 UserProfile 表取用户资料。注意：这里用的是 `.get()` 而不是 `.filter()`，前者返回单个对象（找不到或找到多个会抛异常），后者返回 Queryset

- `refresh = RefreshToken.for_user(user)` —— 为登录成功的用户**生成一对 JWT**。`for_user()` 同时创建 Access Token 和 Refresh Token。Token 里编码了用户 id 等信息，服务器解码后就能知道是谁在发请求

- `response = Response({...})` —— 构建 JSON 响应。因为前端需要存用户信息，所以除了 token 还返回了 `user_id`、`username`、`photo`（头像 URL）、`profile`（个性签名）

- `user_profile.photo.url` —— 注释写了 `# 必须加url！！！`。`user_profile.photo` 是 `ImageField` 对象，`.url` 属性返回文件的可访问 URL（如 `/media/user/photos/1_abc.png`）。如果只写 `user_profile.photo`，序列化时会得到一个文件对象而不是 URL 字符串

- `response.set_cookie(...)` —— 在响应里**设置 Cookie**。浏览器收到这个响应头后，会自动把 cookie 存起来，后续每次请求这个域名时自动带上。
  - `key='refresh_token'` —— Cookie 名称
  - `value=str(refresh)` —— JWT Refresh Token 的字符串形式
  - `httponly=True` —— **安全关键**。标记后 JavaScript 完全无法用 `document.cookie` 读取这个 Cookie，只能由浏览器自己在发 HTTP 请求时自动携带。这样即使网页被 XSS 攻击注入恶意脚本，也无法偷走 Refresh Token
  - `samesite='Lax'` —— 同站策略。`Lax` 表示仅在用户从其他网站导航到本网站时允许发送 Cookie（如点链接），但在跨站 AJAX 请求中不发送。平衡了安全和用户体验
  - `secure=True` —— 只在 HTTPS 连接中发送。开发阶段用 HTTP 也能设置成功（Django 开发服务器宽松处理），但生产必须配合 SSL
  - `max_age=86400 * 7` —— Cookie 有效期 7 天（单位：秒）。`86400 = 24×60×60 = 一天`。7 天后浏览器自动删除这个 Cookie，和 Refresh Token 的有效期一致

- `except:` —— 捕获**所有**未知异常。因为 `UserProfile.objects.get()` 可能报 `DoesNotExist`、数据库连接可能失败等。返回一个通用的"系统异常"提示而不是让用户看到 500 错误页面

## 七、注册接口——`RegisterView`

**文件**：`backend/web/views/user/account/register.py`

```python
from django.contrib.auth.models import User
from rest_framework.response import Response
from rest_framework.views import APIView
from rest_framework_simplejwt.tokens import RefreshToken

from web.models.user import UserProfile


class RegisterView(APIView):
    def post(self, request):
        try:
            username = request.data['username'].strip()
            password = request.data['password'].strip()
            if not username or not password:
                return Response({
                    'result': '用户名和密码不能为空'
                })
            if User.objects.filter(username=username).exists():
                return Response({
                    'result': '用户名已存在'
                })
            user = User.objects.create_user(username=username, password=password)
            user_profile = UserProfile.objects.create(user=user)
            refresh = RefreshToken.for_user(user)
            response = Response({
                'result': 'success',
                'access': str(refresh.access_token),
                'user_id': user.id,
                'username': user.username,
                'photo': user_profile.photo.url,
                'profile': user_profile.profile,
            })
            response.set_cookie(
                key='refresh_token',
                value=str(refresh),
                httponly=True,
                samesite='Lax',
                secure=True,
                max_age=86400 * 7,
            )
            return response
        except:
            return Response({
                'result': '系统异常，请稍后重试'
            })
```

**与登录不同的地方：**

- `request.data['username']` —— 这里用 `[]` 取而不是 `.get()`。如果字段不存在会直接报 `KeyError`，进入 `except` 返回"系统异常"。而登录用的是 `.get()` 然后判断 None。两种风格都可以，`[]` 更严格

- `User.objects.filter(username=username).exists()` —— **检查用户名是否已被占用**。`.filter()` 即使没有匹配结果也不报错，返回空 Queryset；`.exists()` 检查是否有结果，有返回 `True`。**为什么不用 `.get()`**：`.get()` 在找不到时抛出 `DoesNotExist` 异常，需要用 try/except 包起来，代码更啰嗦

- `User.objects.create_user(username=username, password=password)` —— Django 的**创建用户专用方法**。不要用 `User.objects.create()`——后者会把密码明文存到数据库！`create_user()` 内部会调用 `set_password()`，把密码通过 **bcrypt/PBKDF2 等哈希算法**加密后再存。数据库中永远不存明文密码。（什么是"哈希"？哈希是一种单向加密——把密码"张三123"经过算法变成一长串乱码如`$2b$12$LJ3m...`，这个过程不可逆，无法从乱码反推出原始密码。登录时，Django把你输入的密码再哈希一次，和数据库里的哈希值比较——如果一致就说明密码正确。即使数据库被盗，黑客只能看到哈希乱码而看不到原始密码，因为哈希不可逆推。就像把一张纸烧成灰——灰是哈希，你无法从灰还原原纸，但如果有人给你另一张纸，你能烧了对比灰是不是一样。明文存储如果数据库泄露，所有用户的密码直接暴露；哈希存储即使泄露，黑客也拿不到原始密码）

- `UserProfile.objects.create(user=user)` —— 用 `.create()` 同时实例化和保存。等价于：
  ```python
  user_profile = UserProfile(user=user)
  user_profile.save()
  ```
  一个方法搞定，更简洁。注意这里只传了 `user`，其他字段（`photo`、`profile`）用模型定义的默认值（默认头像 + 默认签名）

- 注册成功后**直接登录**——和登录接口一样生成 JWT、设置 Cookie、返回用户信息。用户注册完不需要再输入密码登录一次

## 八、退出接口——`LogoutView`

**文件**：`backend/web/views/user/account/logout.py`

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated


class LogoutView(APIView):
    permission_classes = [IsAuthenticated]  # 强制必须登录才能访问
    def post(self, request):
        response = Response({
            'result': 'success'
        })
        response.delete_cookie('refresh_token')
        return response
```

**逐行讲解：**

- `permission_classes = [IsAuthenticated]` —— DRF 的权限控制。`IsAuthenticated` 要求请求必须携带有效的 JWT Access Token（通过 `Authorization: Bearer xxx` 头部）。没登录的人访问这个接口直接返回 401。**为什么要登录才能退出**：没登录的人没有 refresh_token Cookie，不需要退出

- `response.delete_cookie('refresh_token')` —— 告诉浏览器删除指定名称的 Cookie。Django 通过设置一个过期时间为 1970 年的 Cookie 来实现（等同于删除）

**退出逻辑本质上就一步**：删除浏览器中的 Refresh Token Cookie。后续请求因为没有有效的 Refresh Token，即使用户保存了旧的 Access Token，一旦 Access Token 过期（2小时）就无法自动刷新，必须重新登录。

## 九、刷新令牌接口——`RefreshTokenView`

**文件**：`backend/web/views/user/account/refresh_token.py`

```python
from django.conf import settings
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework_simplejwt.tokens import RefreshToken


class RefreshTokenView(APIView):
    def post(self, request):
        try:
            refresh_token = request.COOKIES.get('refresh_token')
            if not refresh_token:
                return Response({
                    'result': 'refresh token不存在'
                }, status=401)
            refresh = RefreshToken(refresh_token)
            if settings.SIMPLE_JWT['ROTATE_REFRESH_TOKENS']:
                refresh.set_jti()
                response = Response({
                    'result': 'success',
                    'access': str(refresh.access_token),
                })
                response.set_cookie(
                    key='refresh_token',
                    value=str(refresh),
                    httponly=True,
                    samesite='Lax',
                    secure=True,
                    max_age=86400 * 7,
                )
                return response
            return Response({
                'result': 'success',
                'access': str(refresh.access_token),
            })
        except:
            return Response({
                'result': "refresh token过期了"
            }, status=401)
```

**逐行讲解：**

- `request.COOKIES.get('refresh_token')` —— 从请求携带的 Cookie 中读取 Refresh Token。注意是 `COOKIES`（全大写复数），这是 Django `HttpRequest` 的属性，包含了请求中所有 Cookie 的字典

- `if not refresh_token:` → 返回 401 —— Cookie 中没有 Refresh Token（可能已经过期被浏览器自动清理了，或者根本没登录）

- `refresh = RefreshToken(refresh_token)` —— 从 Cookie 中取出的字符串**重新构造** JWT 对象。构造过程中会自动验证签名和有效期。如果 Refresh Token 过期、被篡改、或格式不对，抛出异常进入 `except` 分支。（JWT怎么防伪造？JWT由三部分组成用`.`连接：`头部.载荷.签名`。头部和载荷只是base64编码（相当于明文），任何人都能解码看里面的内容。关键的防伪措施在第三部分"签名"——服务器用密钥对"头部+载荷"算出一个哈希值附在后面。如果有人篡改了载荷（比如把`user_id: 123`改成`user_id: 456`），签名就对不上了，服务器验证时直接拒绝。简单说：JWT内容你可以看但不能改——改了签名就穿帮。就像一张盖章的文件，你可以读上面写的字，但改了内容印章就对不上了）

- `if settings.SIMPLE_JWT['ROTATE_REFRESH_TOKENS']:` —— 检查 settings.py 里的配置。`ROTATE_REFRESH_TOKENS = True` 的意思是每次用 Refresh Token 刷新 Access Token 时，**老 Refresh Token 作废，发放一个新的 Refresh Token**。这是安全措施：如果有人曾截获了一次 Refresh Token，Token 轮换后旧的就没用了

- `refresh.set_jti()` —— 给新的 Refresh Token 设置唯一标识（JTI = JWT ID），使旧的失效

- `status=401` —— HTTP 401 状态码（未授权）。前端根据这个状态码判断"用户需要重新登录"，自动跳转到登录页。注释写了 `# 必须加401`——如果不加，DRF 默认返回 200，前端无法区分正常响应和认证失败

## 十、你注意到的一个 bug

`LoginView` 中这行：
```python
user_profile = UserProfile.objects.get(username=username)
```

`UserProfile` 表里**没有 `username` 字段**！`username` 在 `User` 表里，`UserProfile` 通过 `user`（OneToOneField）关联 User。正确的查询应该是：
```python
user_profile = UserProfile.objects.get(user=user)
```

这行暂时没报错是因为 SQLite 对这个查询"比较宽容"——Django ORM 生成的 JOIN 查询中 username 被自动关联了。但在严格模式下或换用 PostgreSQL/MySQL 会直接报字段不存在的错误。后续提交应该修复。

## 十一、总结

| 接口 | URL | 方法 | 做了什么 |
|------|-----|------|---------|
| 注册 | `/api/user/account/register/` | POST | 创建 User + UserProfile，返回 JWT + 用户信息，设 Cookie |
| 登录 | `/api/user/account/login/` | POST | 验证密码，返回 JWT + 用户信息，设 Cookie |
| 退出 | `/api/user/account/logout/` | POST | 删除 Cookie（需登录） |
| 刷新 | `/api/user/account/refresh_token/` | POST | 用 Cookie 中的 Refresh Token 换新的 Access Token |

**安全设计**：
- Refresh Token → HttpOnly Cookie（JS 无法读，防 XSS）
- Access Token → JSON 响应体（前端存内存，用于 API 鉴权）
- ROTATE_REFRESH_TOKENS → 每次刷新换新 Token（防长期盗用）
