## 一、这次提交做了什么

实现了**聊天的后端核心**——引入 LangChain + LangGraph 框架，创建 AI 对话工作流。用户发消息 → 后端调用 DeepSeek 大模型 → 返回 AI 回复。这是整个项目的灵魂——前面的所有工作（用户系统、角色系统、好友系统）都是为这一步服务的。（什么是大语言模型LLM？简单说就是一个"超级接话机器人"——你给它一段文字，它预测接下来最合适的文字是什么。比如你问"今天天气怎么样"，它在海量文本中学到过类似问答，会生成"今天天气晴朗，适合出门"。不同的是这个机器人读了几乎整个互联网的文本，所以什么话题都能接。DeepSeek v3.2就是这样一个模型，由中国的深度求索公司训练。LangChain是什么？一个Python工具库，让你方便地调用各种大模型——不管底层是OpenAI/DeepSeek/通义千问，都用同一套代码`ChatOpenAI(model='xxx')`来调用，不用每次学不同的API格式。LangGraph是什么？在LangChain基础上加了"工作流"能力——你可以画一张流程图，定义"先执行A步骤，然后根据结果决定走B还是C"，AI按照你画的图一步步执行。这比简单的"发消息→等回复"灵活得多）

## 二、使用了什么技术

| 技术 | 用途 |
|------|------|
| LangChain `ChatOpenAI` | 统一 LLM 调用接口（实际调 DeepSeek，但 OpenAI 兼容 API） |
| LangGraph `StateGraph` | 工作流引擎，构建节点+边的有向图执行 AI 调用 |
| `TypedDict` + `Annotated[Sequence, add_messages]` | 定义 Agent 状态，`add_messages` 自动合并多节点产出的消息 |
| DeepSeek v3.2 | 实际使用的大语言模型 |
| `python-dotenv` `.env` | API 密钥与环境变量管理 |

## 四、源码

### 4.1 `graph.py`——LangGraph 工作流（新文件，32行）

```python
import os
from typing import TypedDict, Annotated, Sequence

from langchain_core.messages import BaseMessage
from langchain_openai import ChatOpenAI
from langgraph.constants import START, END
from langgraph.graph import add_messages, StateGraph


class ChatGraph:
    @staticmethod
    def create_app():
        llm = ChatOpenAI(
            model='deepseek-v3.2',
            openai_api_key=os.getenv('API_KEY'),
            openai_api_base=os.getenv('API_BASE'),
        )

        class AgentState(TypedDict):
            messages: Annotated[Sequence[BaseMessage], add_messages]

        def model_call(state: AgentState) -> AgentState:
            res = llm.invoke(state['messages'])
            return {'messages': [res]}

        graph = StateGraph(AgentState)
        graph.add_node('agent', model_call)

        graph.add_edge(START, 'agent')
        graph.add_edge('agent', END)

        return graph.compile()
```

**逐行讲解**：

- `from langchain_openai import ChatOpenAI` —— LangChain 的 OpenAI 兼容客户端。虽然实际调的是 DeepSeek，但 DeepSeek 实现了 OpenAI 兼容 API（`/v1/chat/completions` 端点），所以用这个类就行。`openai_api_base` 指向 DeepSeek 的地址就能切换模型
- `model='deepseek-v3.2'` —— DeepSeek 最新版本模型
- `openai_api_key=os.getenv('API_KEY')` —— 从环境变量读取 API 密钥。`.env` 文件里 `API_KEY=sk-xxx`，`load_dotenv()` 加载后 `os.getenv` 就能读到。（什么是`.env`和环境变量？API密钥就像银行卡密码，绝对不能写在代码里提交到Git——否则代码一旦公开，别人就能用你的密钥调用AI服务、产生费用。`.env`是一个不提交到Git的文件（.gitignore里排除了它），里面存敏感配置：`API_KEY=sk-xxxxxxxx`。`python-dotenv`库在程序启动时读取这个文件，把内容注入到系统环境变量中。代码里用`os.getenv('API_KEY')`读取，这样密钥和代码分离，安全且在不同环境（开发/生产）切换方便——换一套密钥只需改`.env`文件，不用改代码）
- `openai_api_base=os.getenv('API_BASE')` —— API 基础 URL，指向 DeepSeek 服务器
- `class AgentState(TypedDict):` —— 定义状态结构。`TypedDict` 是 Python 类型提示，告诉类型检查器这个字典有什么键、什么类型。LangGraph 用它来约束状态的形状
- `messages: Annotated[Sequence[BaseMessage], add_messages]` —— `Annotated[类型, 合并器]`。`add_messages` 是 LangGraph 内置函数，当多个节点都返回 `{'messages': [新消息]}` 时，用 `add_messages` 把新消息**追加**到已有列表，而不是覆盖。（为什么要用Annotated+add_messages？想象一个公告板——多个节点往上面贴纸条，普通做法是后贴的纸条把先贴的盖掉（覆盖）；`add_messages`的做法是把新纸条贴在旧纸条下面（追加）。在对话场景中这很关键——用户说了A、AI回了B、用户又问C，如果每次返回新消息时覆盖旧消息，AI就看不到前面的对话历史了。`add_messages`确保消息列表像聊天记录一样持续增长，不会丢失前面的内容。`Annotated`是Python的类型注解语法——`Annotated[原始类型, "元数据"]`，这里用它告诉LangGraph"messages这个字段用add_messages来合并"）
- `def model_call(state) -> AgentState:` —— 节点函数。参数是当前状态，返回值是状态更新。LangGraph 用返回值更新状态后再传给下一个节点
- `res = llm.invoke(state['messages'])` —— **同步调用** LLM。`invoke` 阻塞直到 AI 生成完整回复。`state['messages']` 是整个消息列表，AI 看到所有消息后生成回复
- `return {'messages': [res]}` —— 返回 AI 的回复消息。`add_messages` 会把它追加到 `state['messages']`
- `graph = StateGraph(AgentState)` —— 创建以 `AgentState` 为状态类型的图。（什么是StateGraph？就像画流程图——你先定义"数据长什么样"（AgentState，一个装着消息列表的字典），然后画圆圈（节点，每个节点是一个函数）和箭头（边，表示执行顺序）。`add_node('agent', model_call)`画了一个叫"agent"的圆圈，`add_edge(START, 'agent')`从起点画箭头指向它，`add_edge('agent', END)`从它画箭头指向终点。`compile()`就是"确认图纸，开始执行"。数据（消息列表）沿着箭头流动，每个圆圈处理数据后传给下一个。当前只有一条直线：START → agent → END。后面会加入分支和循环，让图变得更复杂）
- `graph.add_node('agent', model_call)` —— 添加节点 `'agent'`，绑定 `model_call`
- `graph.add_edge(START, 'agent')` —— START → agent
- `graph.add_edge('agent', END)` —— agent → END
- `graph.compile()` —— 编译为可执行对象

**此时的工作流**：START → agent（调一次 LLM）→ END。最简单的链式调用，无工具、无循环。

### 4.2 `chat.py`——聊天 API 视图（新文件，35行）

```python
from langchain_core.messages import HumanMessage
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated

from web.models.friend import Friend
from web.views.friend.message.chat.graph import ChatGraph


class MessageChatView(APIView):
    permission_classes = [IsAuthenticated]
    def post(self, request):
        friend_id = request.data['friend_id']
        message = request.data['message'].strip()
        if not message:
            return Response({
                'result': '消息不能为空'
            })
        friends = Friend.objects.filter(pk=friend_id, me__user=request.user)
        if not friends.exists():
            return Response({
                'result': '好友不存在'
            })
        friend = friends.first()
        app = ChatGraph.create_app()

        inputs = {
            'messages': [HumanMessage(message)]
        }
        res = app.invoke(inputs)
        print(res['messages'][-1].content)

        return Response({
            'result': 'success',
        })
```

**逐行讲解**：

- `friend_id = request.data['friend_id']` —— 用 `[]` 取值，字段不存在则 KeyError → DRF 异常处理返回 400
- `message = request.data['message'].strip()` —— 去首尾空格
- `if not message:` —— 空字符串判断。`not ""` = `True`
- `Friend.objects.filter(pk=friend_id, me__user=request.user)` —— 权限校验。只查当前用户的好友关系。别人创建的好友关系即使知道 friend_id 也查不到
- `if not friends.exists():` —— 好友关系不存在 → 返回错误
- `app = ChatGraph.create_app()` —— 每次请求创建新的工作流实例。LangGraph 的图是无状态的，每次调用可以复用，这里每次新建是为了确保隔离
- `inputs = {'messages': [HumanMessage(message)]}` —— 构造输入。用户消息包装为 `HumanMessage`
- `res = app.invoke(inputs)` —— 执行工作流，同步阻塞等 AI 回复
- `res['messages'][-1].content` —— 最后一条消息（AI 的 AIMessage）的文本内容
- `print(...)` —— **只在服务器终端打印**，前端收不到 AI 回复！
- `return Response({'result': 'success'})` —— 只返回成功标志，没返回 AI 回复内容

**这个版本的已知问题**：
- 没有系统提示词 → AI 不知道角色是谁
- 没有历史对话 → 每次是"初次见面"
- 没有流式输出 → 用户等全部生成完才能看到
- AI 回复只在终端打印 → 前端看不到
- 没有 tool calling
